## Task → staging PR → approval → main PR

1. Fetch `origin/main`; make a task branch in its own worktree. Reproduce, implement, test/build, and review. Record the tested task-branch SHA. Keep one task at a time in the **awaiting-staging-verification/approval** slot. Before merging into staging, atomically create an exclusive lock outside Git with the repository, task, staging PR, and full head SHA; never overwrite an active lock. Keep a separate durable private task record. Other implementation work must not overwrite this lock, its record, or shared staging evidence.
2. Open a PR with `base=staging`, `head=<task-branch>`. Record the task-head SHA and task-specific changed files/hunks. Document an agent review of the full diff with no unresolved blocking findings; a separate human review is not required for this demo. Require successful `Store checks` on the current PR head, no conflicts or unrelated changes, and the exclusive staging-task lock before merging. Respect any actual branch protections. Resolve conflicts without pulling unrelated staging changes into the task branch destined for `main`. **Do not delete the task branch.** Record the resulting `staging` SHA; it may differ from the PR head because of the merge strategy.
3. Wait for the `Store checks` **push** run on the resulting `staging` SHA to pass, then for `orbit-store-stagging` to deploy the **same SHA** automatically to its testing website. Read back deployment/project/domain/SHA and run health and interactive checks there. Identify staging-only changes separately: the staged tree may contain commits absent from the task branch and from the future main PR. Ask the verifiably authorized user to verify the **task-specific delta** and its behavior, identifying task-head SHA, staging PR, deployed SHA, and website. Do not present the entire testing website as byte-identical to the future main release or treat merge/preview as approval.
4. After explicit approval of that task-specific delta and tested task-head SHA, recheck that the head has not moved. Compare the proposed main PR's changed files/hunks and base context with the approved task delta and account for staging-only commits and dependencies. If the behavior would differ materially on `main`, stop: bring the necessary code through reviewed task changes, re-test in staging, and obtain fresh approval. Open a **second PR from the same task branch**, `base=main`; review, wait for its required checks/reviews, and merge only if the approved scope is unchanged. If commits or behavior changed, revalidate staging and obtain fresh approval. Keep the task branch until both PRs complete; do not delete it on either PR merge until both completion records have been checked.
5. Watch the existing production project's automatic deployment of the actual resulting `main` merge SHA. Read back its deployment ID, source SHA, domain, readiness, and health/functional result. Report the two PRs, staged verification/approval, production URL/SHA, and actual checks. On failure, report the real status and request an authorized restoration decision rather than declaring success.
